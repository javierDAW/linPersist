# Benchmark v0.1.0-alpha · realistic-fleet detection envelope

> What linpersist v0.1.0-alpha catches and what it misses on a
> heterogeneous 75-host fleet that simulates real production noise.
> The headline is not "linpersist works" — it is **"linpersist's LFA
> primitives have specific failure modes that v0.2.0 must address."**

## TL;DR

| Detector | Precision | Recall | F1 | Operational verdict |
| --- | --- | --- | --- | --- |
| **Q4 ∪ Q9** | **1.00** | **1.00** | **1.00** | Primary tmp-implant detector. Ship as-is. |
| Q4 alone | 1.00 | 1.00 over orphan-tmp | 1.00 | Specialist; pair with Q9. |
| Q9 alone | 1.00 | 1.00 over any-tmp | 1.00 | Specialist; pair with Q4. |
| Q7 | 0.14 | 1.00 over signal clauses | 0.25 | Recall-complete, precision crashed. Needs v0.2.0 refinements. |
| **Q1 / Q2** | **0.00** | **0.00** | 0.00 | **Blind to mass-deployment.** Triage indicators only. |
| Q6 (manual) | ≈ 0.02 | 1.00 | ≈ 0.05 | Needs `spread_min ≥ 2` filter. |
| Q3 | n/a | n/a | n/a | No implant declared in catalog; over-fires on per-distro baselines. |

**Four findings load this report:**

1. **LFA singletons (Q1, Q2) fail against mass-deployed implants.**
   When `N > 1` hosts carry the same implant template, the
   `content_norm_sha256` stacks like any baseline configuration and
   the implant disappears from the long tail. Demonstrated with a
   4-host coordinated implant whose normalized content hash collapses
   to a single value across all four. Recall = 0.
2. **Q4 ∪ Q9 is a perfect detector at 75 hosts.** No legitimate
   package configuration in a fleet of 75 mixed Debian / Ubuntu /
   RHEL (UBI9) / Amazon Linux / Alpine hosts produced a record with
   `exec_target` under `/tmp/*` (Q9) or `exec_target_orphan +
   interpreter_in_tmp` simultaneously (Q4). Both detectors achieved
   precision 1.00 and recall 1.00 over their declared scope.
3. **Q7's signal-clause recall comes at a 0.14 precision cost.**
   The 95 false positives concentrate on `/etc/sudoers` root
   entries (~60), legitimate CI NOPASSWD sudoers.d entries (~5),
   and per-distro `modprobe.d` `install` directives (~30). Recall
   stays 1.00 over the signal-based implants (sudoers, passwd,
   kmod) but the analyst trial cost is prohibitive without
   refinement.
4. **Q6 (worm pattern) needs a `spread_min ≥ 2` filter to be
   useful.** At 75 hosts the unfiltered query yields 43 hits, only
   one of which is the seeded worm-shared trio (3 hosts × different
   vectors). The other 42 are shared distro-package binaries
   (`/etc/init.d/prometheus-node-exporter`, `/sbin/fstrim`, etc.)
   that appear identical across hosts of the same distro.

The remainder of this document lays out the methodology, the per-query
results, the false-positive analysis, the lab's caveats, and four
concrete refinements that the v0.2.0 release is justified to make.

## Methodology

### Lab name and scope

`lab-realistic/` is a Docker-based reproducible benchmark fleet held
locally in the project repository under `.gitignore`. It is NOT
shipped with the public project. The benchmark *results* — this
document — are versioned; the lab infrastructure that produced them
is not, primarily because: (a) the package versions resolved by
`apt`/`dnf`/`apk` at any given moment change over time and are not
reproducible without a frozen package mirror; (b) the rationale for
the lab is to measure precision/recall on real distro noise, and
that noise IS the per-build snapshot of upstream archives.

### Fleet composition

The fleet is 75 hosts distributed across 5 Linux distributions and 7
operational roles. Each `(role, distro)` cell has a fixed integer
host count defined in `lab-realistic/policies/realistic-100.yaml`
(the file kept its original name when the host count was scaled down
from 100 to 75 for disk-pressure reasons during the run).

| Role | Debian 12 | Ubuntu 22.04 | RHEL 9 (UBI9) | Amazon Linux 2023 | Alpine 3.20 | **Total** |
| --- | --: | --: | --: | --: | --: | --: |
| `web` | 4 | 4 | 4 | 4 | 3 | **19** |
| `db` | 3 | 3 | 0 | 3 | 0 | **9** |
| `k8s-node` | 4 | 6 | 4 | 4 | 1 | **19** |
| `build-server` | 2 | 2 | 1 | 1 | 0 | **6** |
| `jump` | 1 | 1 | 1 | 0 | 1 | **4** |
| `monitoring` | 3 | 3 | 0 | 2 | 0 | **8** |
| `dev` | 3 | 4 | 2 | 1 | 0 | **10** |
| **Total** | **20** | **23** | **12** | **15** | **5** | **75** |

Two `(role, distro)` cells are explicitly zero: `db on rhel9` and
`monitoring on rhel9`. The reason is documented in *Lab caveats*
below; in short, UBI9 (Red Hat Universal Base Image 9) is a
deliberately restricted subset of RHEL 9 that does not expose the
modular streams those roles require (postgresql, redis, prometheus2,
golang-github-prometheus-*). In a real production fleet those roles
would run on full RHEL with a subscription, or on Rocky/Alma Linux 9.
For the lab we excluded them rather than introduce a heavyweight
substitute that would muddy the comparison.

### Role overlays

Each role installs a curated set of packages chosen to mimic what a
production sysadmin would put on that host. Roles do not start
services — the containers run only long enough for the linpersist
agent to walk the filesystem. We rely on the package-installation
side-effects (cron entries, systemd units, modprobe drops, sudoers
entries, profile additions) to produce realistic noise.

Representative installs:

- `web`: nginx, php-fpm, certbot, python3-certbot-nginx, fail2ban,
  modsecurity-crs (where available), logrotate.
- `db`: postgresql + contrib + client, redis-server (Debian/Ubuntu);
  postgresql15-server + postgresql15 + redis6 (Amazon Linux).
- `k8s-node`: containerd, ipset, iptables, socat, conntrack
  (where available); plus an `/etc/modules-load.d/k8s.conf` drop and
  a `/etc/sysctl.d/99-kubernetes-cri.conf` drop emulating what
  `kubeadm init` produces.
- `build-server`: docker.io or `docker`, git, build-essential,
  openjdk-17, python3-pip; plus realistic sudoers.d entries for
  gitlab-runner (NOPASSWD: /usr/bin/docker, /usr/bin/systemctl
  restart gitlab-runner) and jenkins (NOPASSWD: ALL). These
  sudoers entries are NOT implants — they are common in production
  CI fleets and are the primary source of Q7 false positives.
- `jump`: openssh-server (heavily customised), libpam-google-
  authenticator, fail2ban; plus `/etc/ssh/sshd_config.d/10-bastion
  .conf`, `/etc/ssh/sshd_config.d/20-backup-restricted.conf` (with
  a Match block scoping a backup-only group), an authorized_keys
  file with a legitimate forced-command rsync key + per-admin keys,
  and a sudoers entry for the `%ops` group with NOPASSWD on
  `systemctl reload fail2ban` and `journalctl -u sshd`.
- `monitoring`: prometheus, prometheus-node-exporter,
  prometheus-alertmanager.
- `dev`: git, vim-enhanced, jq, python3-pip, nodejs, npm; plus
  per-user `.bashrc` additions for two synthetic developer accounts
  (alice, bob) with realistic PATH exports, GOPATH, kubectl
  completion, KUBECONFIG, and git aliases.

The realistic-noise pieces (jenkins / gitlab-runner NOPASSWD,
bastion Match block, backup forced-command key, per-user .bashrc)
are *deliberately the same shape* as the implant patterns. Q7's
inability to distinguish them is a measured property, not an
oversight in the lab design.

### Drift simulation

A drift step ages `mtime`s on package-installed files back by 0, 45,
or 180 days. Drift runs BEFORE implant placement, so implants land
with the build's current `mtime` (matching the realistic scenario of
a recently-compromised long-running host).

| Drift bucket | Days back | Hosts |
| --- | --: | --: |
| `fresh` | 0 | 22 |
| `lived_in` | 45 | 38 |
| `dusty` | 180 | 15 |

Drift is implemented as `find /etc /usr/sbin /usr/bin /lib
/var/lib/dpkg/info -type f -exec touch -d 'N days ago' {} +` and is
silent on permission/missing-path errors. It is a coarse simulation
of upgrade history; it does NOT model the realistic dpkg/rpm pattern
where some files retain their original mtime through upgrades
because they were unchanged.

### Implant catalog

30 implant instances across 11 distinct implant types. Each implant
is **inert** — a `printf`-based no-op that, IF executed (the lab
never executes implants; the container exits after the linpersist
agent runs), writes a single trace line to `/tmp/.implant-trace`.
There are no payloads, no reverse shells, no network calls.

| ID | Tier | Variant | Module | Instances | Expected to catch |
| --- | --- | --- | --- | --: | --- |
| `cron-tmp-payload` | L1 | armed | cron | 4 | Q1, Q2, Q9 |
| `cron-tmp-dangling` | L1 | orphan | cron | 3 | Q1, Q2, Q4, Q7, Q9 |
| `systemd-tmp-armed` | L1 | armed | systemd | 4 | Q1, Q2, Q9 |
| `systemd-tmp-orphan` | L1 | orphan | systemd | 3 | Q1, Q2, Q4, Q7, Q9 |
| `ssh-forced-tmp` | L1 | armed | ssh | 3 | Q1, Q2, Q9 |
| `sudoers-nopass-attacker` | L1 | armed | sudoers | 4 | Q1, Q2, Q7 |
| `passwd-uid0-backdoor` | L1 | armed | passwd | 3 | Q1, Q2, Q7 |
| `kmod-install-implant` | L2 | armed | kmod | 3 | Q1, Q2, Q7 |
| `worm-shared-cron` | L5 | armed | cron | 1 | Q6 |
| `worm-shared-systemd` | L5 | armed | systemd | 1 | Q6 |
| `worm-shared-profile` | L5 | armed | profile | 1 | Q6 |

**Armed vs orphan** captures the post-compromise state of the
implant:

- *Armed*: the persistence entry references a payload file that
  IS on disk. linpersist sees both the cron entry and the binary.
  `exec_target_orphan` does NOT fire because the file exists.
- *Orphan*: the persistence entry references a payload file that
  is NOT on disk (deleted, never written, or referenced in advance).
  `exec_target_orphan` fires. This is the textbook v0.1.0 Q4 case.

The armed/orphan distinction maps to a real-world choice: a
sophisticated attacker who drops the loader before activation
produces an armed implant; a stale persistence reference left by
a partially-rolled-back compromise produces an orphan one. Both
modes occur in production IR; the benchmark measures both.

**Worm-shared (L5)** is a three-implant set that drops a
byte-identical payload at `/usr/local/sbin/sync-agent` on three
different hosts and invokes it via three different vectors (cron,
systemd, profile.d). The shared payload bytes mean the same
`exec_target_sha256` appears on three hosts with three different
`module` values — the textbook pattern for Q6 (cross-host
`exec_target` stacking with module spread).

### Implant placement and reproducibility

The fleet generator (`scripts/generate_100.py`) is deterministic
under a fixed seed (`seed: 42` in the policy file). Re-running the
generator produces byte-identical `hostlist.yaml` output. Implant
placement honours per-implant filters (role and distro lists)
declared in the policy.

The 30 implant instances are distributed across 27 compromised hosts
(three hosts carry two implants each: `r-build-server-rhel-01`
carries ssh-forced-tmp + sudoers-nopass-attacker;
`r-monitoring-ubu-02` carries systemd-tmp-armed +
sudoers-nopass-attacker; `r-web-amzn-01` carries cron-tmp-payload +
cron-tmp-dangling). 48 hosts are clean — they anchor the
false-positive baseline.

## Top-line results

The analyzer (`lab-realistic/analyzer/`) reads the agent's NDJSON
output, runs Python reimplementations of Q1, Q2, Q3, Q4, Q7, Q9
(mirroring `cmd/linpersist-report/stats.go` and
`tools/stack_demo.sql`), and joins predicted hits against
ground_truth.jsonl produced from `hostlist.yaml` + `catalog.yaml`.
Q5, Q6, Q8, Q10 are aggregate metrics not amenable to per-record
TP/FP measurement; Q6 is discussed separately below.

A predicted (host, locus) tuple is a **true positive** for query Q
if the ground truth has an implant on that host at that locus AND Q
is declared in the implant's `expected_caught_by` set. Hits are
deduplicated to unique (host, locus) tuples before matching to
account for per-line emission (e.g., the cron module emits one
record per line; the implant locus has three records, but the host
+ locus pair is one match.)

### Per-query metrics

| Query | Hits (raw) | Hits (dedup) | TP | FP | FN | Precision | Recall | F1 |
| --- | --: | --: | --: | --: | --: | --: | --: | --: |
| Q1 — LFA singletons | 24 | 21 | 0 | 21 | 8 | 0.00 | 0.00 | 0.00 |
| Q2 — Per-locus singletons | 30 | 24 | 0 | 24 | 8 | 0.00 | 0.00 | 0.00 |
| Q3 — Peer-group by `os_id` | 164 | 86 | 0 | 86 | 0 | n/a | n/a | n/a |
| Q4 — Implant fingerprint | 6 | 6 | 6 | 0 | 0 | **1.00** | **1.00** | **1.00** |
| Q7 — Implant roll-call | 210 | 111 | 16 | 95 | 0 | 0.14 | 1.00 | 0.25 |
| Q9 — Exec in tmp dirs | 17 | 17 | 17 | 0 | 0 | **1.00** | **1.00** | **1.00** |

### Combined detectors

| Combination | TP | FP | FN | Precision | Recall | F1 |
| --- | --: | --: | --: | --: | --: | --: |
| **Q4 ∪ Q9** | 17 | 0 | 0 | **1.00** | **1.00** | **1.00** |
| Q4 ∪ Q7 ∪ Q9 | 27 | 90 | 0 | 0.23 | 1.00 | 0.37 |
| Q1 ∪ Q2 | 0 | 28 | 8 | 0.00 | 0.00 | 0.00 |

Q4 ∪ Q9 catches every implant whose `expected_caught_by` set
includes Q4 or Q9 (17 instances: cron-tmp-payload ×4, cron-tmp-
dangling ×3, systemd-tmp-armed ×4, systemd-tmp-orphan ×3,
ssh-forced-tmp ×3). It produces zero false positives.

Q4 ∪ Q7 ∪ Q9 adds Q7's coverage of the non-tmp implants (sudoers,
passwd, kmod = 4 + 3 + 3 = 10 instances) for a combined TP count of
27 out of 27 implants where any of these three queries is expected
to catch. Precision drops to 0.23 because Q7 contributes 95 false
positives that neither Q4 nor Q9 sees.

The three worm-shared (Q6-expected) instances are not in this
table; Q6 was not run through the analyzer in this round.

## Findings

### Finding 1 (load-bearing) — LFA singletons fail against mass-deployed implants

Q1 (LFA singletons) is the load-bearing query of the linpersist
detection model. Its premise is that an attacker's persistence
artefacts are unique per host and therefore appear in the long tail
of the `content_norm_sha256` distribution. The cookbook describes
Q1 as the first query an analyst should run.

**This benchmark falsifies that premise under the most common
attacker pattern.** When the same implant template lands on
multiple hosts — exactly what a worm, an automated post-exploitation
toolkit, or a coordinated supply-chain attack produces — the
canonical `content_norm_sha256` collapses to a single value across
all compromised hosts. The hash count is N, not 1. Q1 does not see
it.

Concrete measurement: the `cron-tmp-payload` template lands on four
hosts (`r-monitoring-ubu-01`, `r-web-alp-01`, `r-web-amzn-01`,
`r-web-deb-04`). All four produce a cron.d record at
`/etc/cron.d/sync-helper` with the identical schedule line
`*/15 * * * * root /tmp/.cache/.sync/agent --backpressure 20`. The
normalized content hash is byte-identical across the four. Q1 sees
the hash four times — not a singleton, not in the long tail.

The same applies to `cron-tmp-dangling` (3 hosts, 1 distinct norm),
`systemd-tmp-armed` (4 hosts, 1 norm), `systemd-tmp-orphan` (3
hosts, 1 norm), `ssh-forced-tmp` (3 hosts, 1 norm),
`sudoers-nopass-attacker` (4 hosts, 1 norm), `passwd-uid0-backdoor`
(3 hosts, 1 norm), `kmod-install-implant` (3 hosts, 1 norm). Every
implant type with `count > 1` in the catalog escapes Q1 by design.

Q2 (per-locus singletons) has the same problem: it groups by
`(module, site_class, locus, content_norm_sha256)`. When the same
template lands at the same locus on multiple hosts (which is the
normal case for an implant — the attacker doesn't randomise the
locus per host), Q2 stacks the same way Q1 does.

**The Q1 false positives — 21 records that aren't implants — are
the OTHER side of the same coin.** Every host has 1–2 records that
are uniquely shaped per host: `hostname_hash`, machine-id-derived
content, certain `os-release` permutations, build-specific
distributions. The implants that should be there aren't, and the
records that shouldn't be flagged are.

**Implication.** Q1 is mis-positioned as a primary detector. It
should be re-classified as a fleet-overview tool: "show me the
content-shape diversity in my fleet." Used that way the 21 hits
are not false positives, they are the expected count of per-host
unique content in a 75-host fleet — about 0.3 unique records per
host, which is healthy.

**v0.1.0 implication for the cookbook.** The line "Q1 is the
load-bearing query" in `docs/stacking-cookbook.md` must be revised.
Q1 detects *bespoke* implants (one host, one specific shape) and is
useless against *mass-deployed* implants (one template, many hosts).
Real attackers in production overwhelmingly use the latter.

### Finding 2 — Q4 ∪ Q9 is the operational primary detector

The combination of Q4 (`exec_target_orphan AND interpreter_in_tmp`)
and Q9 (`exec_target` starts with `/tmp/`, `/var/tmp/`, `/dev/shm/`,
or `/run/shm/`) achieved **precision 1.00 / recall 1.00 / F1 1.00**
over its declared scope of 17 implant instances.

Q4 alone caught the 6 orphan-style instances (cron-tmp-dangling ×3,
systemd-tmp-orphan ×3). Q9 alone caught all 17 instances whose
`exec_target` resolves to a tmp-class directory. Q4 ⊂ Q9 because the
orphan implants' `exec_target` paths are also in `/tmp/*`. The
union deduplicates to 17.

**Zero false positives.** No legitimate package configuration in
the 75-host fleet produced a record where `exec_target` resolves
to `/tmp/*`. We expected at least one or two — some upgrade scripts
write temporary files there, some installer hooks reference them —
but none made it into a persistence locus that the agent walks
(`/etc/cron.d/`, `/etc/systemd/system/`, `/etc/init.d/`,
`/etc/modprobe.d/`, `/etc/udev/rules.d/`, etc.). The 5-distro mix
exercised here is a strong test: each distro's package archive
emits hundreds of cron.d / systemd unit / pam.d / modprobe.d
artefacts; none of them legitimately reference `/tmp/` as an
`exec_target`.

**Operational recommendation.** Q4 ∪ Q9 is shippable as v0.1.0's
primary detection signal for tmp-based persistence. It is the
detector the cookbook's "Triage order" section should lead with.

**Caveat: the worm-shared implants are NOT in Q4 ∪ Q9's scope.**
Their payload lives at `/usr/local/sbin/sync-agent`, not in /tmp.
Q9's prefix list does not include `/usr/local/sbin/`. Adding
`/usr/local/sbin/`, `/opt/`, and other non-package paths to Q9
would push precision down (legitimate `prometheus-node-exporter`,
`certbot`, ad-hoc binary installs all live in those directories).
The right home for worm detection is Q6, not Q9.

### Finding 3 — Q7 trades precision for recall

Q7 is the cross-cutting "implant roll-call" query: a union of seven
disjoint clauses, each designed to catch a class of implants the
others miss. The clauses are:

1. `exec_target_orphan AND interpreter_in_tmp` (the Q4 condition).
2. `sudoers_nopasswd` signal present.
3. `sudoers_all_commands` signal present.
4. `passwd_uid_zero` signal present.
5. `kmod_install_directive` signal present.
6. `module = 'profile' AND content_snippet contains 'curl' OR 'wget'`.
7. `module = 'sysv' AND content_snippet contains '/tmp/'`.
8. `module = 'motd' AND content_snippet contains 'curl' OR 'wget'`.

At 75 hosts Q7 produces 111 unique (host, locus) hits. **16 are
true positives** — the 7 implant types whose `expected_caught_by`
declares Q7 (cron-tmp-dangling ×3, systemd-tmp-orphan ×3,
sudoers-nopass-attacker ×4, passwd-uid0-backdoor ×3,
kmod-install-implant ×3 = 16; ssh-forced-tmp does NOT declare Q7
because clause 1 requires orphan which armed ssh implants don't
fire). **95 are false positives.**

The false positives fall into three buckets:

**Bucket A: `/etc/sudoers` root entries (≈ 70 FPs).** Every Debian
/ Ubuntu / RHEL / Amazon Linux host ships `/etc/sudoers` with at
least these two lines:

```
root    ALL=(ALL:ALL) ALL
%sudo   ALL=(ALL:ALL) ALL          # Debian / Ubuntu
%wheel  ALL=(ALL) ALL              # RHEL / AmazonLinux
```

Both lines fire `sudoers_all_commands`, which is Q7 clause 3. With
70 non-Alpine hosts in the fleet, that's ~140–150 records firing
clause 3. The analyzer's `(host, locus)` deduplication compresses
them down to ~70 unique tuples because both root and group entries
share the locus `/etc/sudoers`. Every one of those 70 is a true
positive for clause 3's signal definition and a false positive for
the detection intent.

**Bucket B: legitimate NOPASSWD sudoers.d entries (≈ 8 FPs).** The
`build-server` role overlay deliberately seeds two realistic
production CI sudoers.d entries:

```
gitlab-runner ALL=(ALL) NOPASSWD: /usr/bin/docker
gitlab-runner ALL=(ALL) NOPASSWD: /usr/bin/systemctl restart gitlab-runner
jenkins       ALL=(ALL) NOPASSWD: ALL
```

The `jump` role overlay seeds:

```
%ops ALL=(ALL) NOPASSWD: /usr/bin/systemctl reload fail2ban, /usr/bin/journalctl -u sshd
```

These fire `sudoers_nopasswd` (Q7 clause 2). With 6 build-server
hosts and 4 jump hosts, that's another 8-12 records firing
legitimately. They are signal-identical to the attacker sudoers
backdoor (`sudoers-nopass-attacker`'s
`cibot-svc ALL=(ALL) NOPASSWD: ALL`).

**Bucket C: legitimate kmod `install` directives (≈ 15 FPs).**
Amazon Linux 2023 and RHEL UBI9 ship multiple `/etc/modprobe.d/`
entries that use the `install` directive for legitimate reasons —
disabling modules by routing through `/bin/true`, replacing kmod
with a userspace wrapper for module-load events, etc. These fire
`kmod_install_directive` (Q7 clause 5) the same way the
`kmod-install-implant` does.

The remaining ≈ 2 FPs are edge cases in passwd ownership signals
that I haven't fully classified.

**The cost of recall.** Q7 catches 100 % of its declared implants
(sudoers, passwd, kmod, profile-with-curl, sysv-with-tmp, motd-with-
curl, and the orphan+tmp class) — the recall column reads 1.00. The
precision pays for it: 16 / 111 = 0.14. Triaging Q7's output
demands the analyst sift seven FPs for every TP. On the 75-host
benchmark this is borderline; on a real 10 000-host fleet the same
ratio means 10 000 records to sift for ~1500 TPs.

**v0.1.0 implication for operators.** Q7 is not a first-pass
detector. Run Q4 ∪ Q9 first; their TPs are guaranteed. Then run Q7
with a filter that excludes the known-noise classes (root /
%wheel / %sudo / %admin sudoers entries; sudoers.d files matching
known service-account names; modprobe.d files shipping from the
distro package).

**v0.2.0 implication.** Three concrete signal refinements (listed in
*v0.2.0 priorities* below) will close ~80 of the 95 FPs without
hurting recall.

### Finding 4 — Q6 needs a `spread_min` filter

Q6 (cross-host `exec_target_sha256` stacking) is designed to catch
the worm pattern: an attacker drops the same payload binary on
multiple hosts and invokes it via different persistence vectors
(cron on host A, systemd on host B, profile on host C). The
unfiltered Q6 catches *any* `exec_target_sha256` shared across
hosts, regardless of how many distinct modules invoke it.

At 75 hosts Q6 returns **43 hits**, of which **1 is the seeded
worm-shared trio** and **42 are legitimate distro-baseline
binaries**. The first row of the output illustrates the noise:

```
exec_target_sha256  hosts  records  modules  sample_target                             spread
d66c020367e8        6      6        1        /etc/init.d/prometheus-node-exporter      sysv
```

`/etc/init.d/prometheus-node-exporter` is installed by the
`prometheus-node-exporter` package on 6 hosts (all monitoring and
some web hosts). All 6 hosts invoke it via the same module
(`sysv`); `spread = 1`. This is not a worm — it's a package
binary.

The seeded worm-shared trio appears in Q6 with `spread = 3`
(cron + systemd + profile) on 3 hosts. It is the only Q6 row with
`spread ≥ 2`. The distinguishing feature exists in the data; Q6
just doesn't filter on it.

**v0.2.0 fix.** Add a `--spread-min N` parameter (default 2) to
the Q6 SQL and the Go-native `computeQ6` function. The 42 FPs
collapse to 0; the 1 TP remains. A parameter rather than a hard-
coded default preserves the operator's ability to inspect
single-module stacking when investigating a specific incident.

## Why Q1 / Q2's FP count is small (and not a contradiction)

A natural question: "if Q1 stacks the implants together, why are
its FP counts only 21 and not, say, hundreds?" Two reasons.

First, the FP count is in unique `(host, locus)` tuples, not raw
records. Many natural singletons (per-host machine-id derived
records, hostname-hashed loci) deduplicate.

Second, the 75-host fleet has substantial *content stacking* across
hosts of the same distro and role. A Debian web host shares ~250
records with another Debian web host because the nginx, certbot,
fail2ban packages produce byte-identical files. Q1's singleton
count therefore represents the per-host *unique* content, which in
a homogeneous-by-role fleet is small — typically the host-id field,
the hostname hash, the machine-id, and 1–2 boot-time artefacts.

A fleet with more heterogeneity per host (manual configurations,
hand-edited files, per-host roles that aren't part of the role
overlay) would push Q1's FP count up. The implant detection
problem doesn't change either way: Q1 detects bespoke implants,
which mass-deployment by definition is not.

## Lab caveats and known limitations

### UBI9 restrictions

Two roles are not viable on the rhel9 image used in this benchmark
because UBI9 (Red Hat Universal Base Image 9) is a deliberately
restricted subset of RHEL 9:

- `db`: postgresql and redis are not exposed via UBI9's modular
  streams. Real RHEL db hosts use full RHEL (with subscription) or
  Rocky/Alma Linux 9.
- `monitoring`: `prometheus2`, `golang-github-prometheus-node-
  exporter`, `golang-github-prometheus-alertmanager` are not in
  UBI9's BaseOS, AppStream, or EPEL 9 (the slim EPEL subset that
  UBI9 can pull). Real RHEL monitoring hosts use full RHEL or pull
  Prometheus from the upstream tarball.

The lab declares these `(role, distro)` cells non-viable in the
policy. The 6 hosts they would have occupied are reassigned to
debian / ubuntu / amzn. A different lab with `rockylinux:9` or
`almalinux:9` images would not have these constraints; the trade-
off was deliberate to keep the benchmark reproducible without
RHEL subscriptions.

Other minor `(role, distro)` cells also degrade rather than fail:
`dev/rhel9` drops `tmux` (not in UBI9 EPEL slim), `jump/rhel9`
drops `mosh` and `tmux`, `k8s-node/rhel9` drops `containerd.io`
(Docker Inc. repo not configured) and `conntrack-tools` (not in
CRB exposed). The role still produces realistic noise from the
packages that DO install.

### Q6 measurement is informal

The analyzer (`run_queries.py`) implements Q1, Q2, Q3, Q4, Q7, Q9
but not Q6, Q5, Q8, Q10. Q5, Q8, Q10 are aggregate metrics not
amenable to per-record TP/FP measurement; Q6 IS per-record amenable
(emit one row per record whose `exec_target_sha256` is in a Q6
group) but was not implemented in this round. The Q6 figures in
this report come from manual inspection of the
`linpersist-report` HTML output. v0.2.0's analyzer should include
Q6 with a `spread_min` parameter so its precision/recall are
measurable inside the confusion matrix.

### Drift simulation is coarse

`find ... -exec touch -d 'N days ago'` ages every package file
identically. Real-world hosts have heterogeneous mtimes: files
unchanged since first install retain their original mtime;
upgraded files have a recent mtime; manually-edited files have
mtimes scattered across the host's history. The lab's drift step
collapses this into one of three buckets (0, 45, 180 days). The
practical consequence is that the `recent_mtime_7d` /
`recent_mtime_30d` signal distribution is more synchronised than
in production. Q8 (mtime concentration) in particular would
behave differently in a fleet with realistic mtime variance.

### 75 hosts vs the original 100-host plan

The benchmark was planned for 100 hosts. Disk pressure on the
Windows host running Docker Desktop forced a reduction to 75 mid-
run. The metrics presented here are for 75. The Q4 ∪ Q9 finding is
robust to the change (precision 1.00 / recall 1.00 are floor
properties — they cannot improve by adding more hosts, only stay
or degrade). Q7's FP scaling is approximately linear in host
count; the 95 FPs reported here would scale to ~125 at 100 hosts
without changing the precision/recall ratio meaningfully.

### Inert implant design

Every implant in the catalog is a no-op: a `printf`-based marker
that emits a single trace line to `/tmp/.implant-trace` if it ever
ran (the lab never runs implants; the container exits after the
agent walks the filesystem). The benchmark measures *on-disk
persistence detection only*. It does not measure:

- Behavioral / process-level detection (linpersist doesn't do this
  in v0.1.0 anyway).
- Anti-forensics: a real attacker would alter file mtimes, link
  the payload through `/proc/<pid>/exe` tricks, hide behind a
  legitimate package name, etc.
- Network-side persistence (C2 callbacks, DNS tunnels): out of
  linpersist's scope.
- AppArmor / SELinux profile abuse: not a v0.1.0 module.

What the benchmark DOES measure: the precision / recall envelope
of the agent's normalization + signal extraction + query layer when
the implant artefacts are exactly the shapes documented in
`docs/schema-v1.md`.

### Single seed, single run

All numbers in this report come from one execution with `seed: 42`.
Running with a different seed would reshuffle implant placement
and change the FP counts moderately (within ±10 % in our
informal earlier checks), but would not affect the per-query
precision figures because Q4 ∪ Q9's 0 FPs and Q1 / Q2's content-
stacking are properties of the agent and the query design, not of
the placement. A formal multi-seed run is deferred to v0.2.0.

## v0.2.0 priorities justified by this benchmark

This benchmark surfaces four concrete agent / query changes that
v0.2.0 should land. Each is justified by a specific data point
above.

### Priority 1 — Refine `sudoers_all_commands` to exclude system entries

**Current behavior.** The signal fires on any sudoers line whose
command spec is `ALL` (modulo aliases), regardless of who the
principal is.

**Data point.** ~70 of the 95 Q7 false positives come from
`root ALL=(ALL) ALL`, `%wheel ALL=(ALL) ALL`, `%sudo ALL=(ALL:ALL)
ALL` entries shipped by every distro's `/etc/sudoers`.

**Proposed change.** `sudoers_all_commands` should NOT fire when
the principal is one of: `root`, `%wheel`, `%sudo`, `%admin`. These
are universal distro defaults. An attacker who needs ALL
permissions adds a NEW principal — that's still caught by
`sudoers_nopasswd` (if NOPASSWD) or by `sudoers_all_commands` for
any non-system principal.

**Expected impact.** Q7 FP count drops from 95 to ~25. Precision
rises from 0.14 to ~0.39. Recall stays 1.00.

### Priority 2 — Add Q7 clause for armed-ssh-in-tmp

**Current behavior.** Q7's only ssh-touching clause is clause 1
(`exec_target_orphan AND interpreter_in_tmp`). Armed ssh implants
with the payload present on disk don't fire orphan, so Q7 misses
them entirely.

**Data point.** The `ssh-forced-tmp` implant has 3 instances; all
3 escape Q7. Q9 catches them but Q9 is module-agnostic; Q7 should
catch them too as a roll-call defense in depth.

**Proposed change.** Add Q7 clause:
`module = 'ssh' AND interpreter_in_tmp`. The
`interpreter_in_tmp` signal fires when a forced-command's path
begins with `/tmp/`, `/var/tmp/`, `/dev/shm/`, or `/run/shm/` —
already implemented in the ssh module.

**Expected impact.** Q7 catches 3 more TPs (the 3 armed-ssh
instances). Q7 false positives unchanged: no legitimate
forced-command in the lab points at a tmp path.

### Priority 3 — ssh module envelope-record on parse failure

**Current behavior.** When linpersist's ssh module encounters a
`/root/.ssh/authorized_keys` (or equivalent) where every key line
fails the parser, it emits zero records and zero errors. The
operator has no signal that the file existed and was unparsable.

**Data point.** During Phase 1 of building this lab, the entire
ssh module emitted 0 records across the fleet because our lab
fixtures used invalid base64 in the public-key blobs. The agent
parsed every line, rejected every line silently, and emitted
nothing. We discovered the bug by reading the source after the
analyzer reported recall = 0 on ssh-forced-tmp; there was no
clue from the NDJSON output.

**Proposed change.** When `processAuthkeysFile` reads a file with
non-zero size and emits zero parsed records, emit an envelope
record with `Errors: [{Field: "content_parse", Code:
"NO_KEYS_PARSED"}]`. The envelope carries the file's mtime,
mode, ownership — operator can decide whether to investigate or
ignore.

**Expected impact.** Bug visibility, no detection-envelope
change. A real-world authorized_keys with all-bad-base64 lines is
rare but it IS a possible attacker tactic (poison the file to
mask a single good attacker key); v0.1.0 currently looks the
other way.

### Priority 4 — Q6 `spread_min` parameter

**Current behavior.** Q6 emits one row per `exec_target_sha256`
that appears on >= 2 hosts (with an upper bound of 10% of the
fleet size, with a kill switch at small fleets). It does not
filter on the number of distinct modules invoking that sha.

**Data point.** Of 43 Q6 hits at 75 hosts, 42 are single-module
stacking (a distro package binary shared across hosts of the
same distro). Only the seeded worm-shared trio has `spread = 3`
(cron + systemd + profile).

**Proposed change.** Add `--spread-min N` (default `2`) to both
`computeQ6` in Go and `tools/stack_demo.sql` Q6. When passed
`--spread-min 2`, only rows with `count(distinct module) >= 2`
appear. The default of 2 makes Q6 a worm detector; passing
`--spread-min 1` recovers the current "any shared exec_target"
behavior for ad-hoc investigation.

**Expected impact.** Q6 FP count drops from 42 to ~0. Precision
rises from ~0.02 to ~1.00. The seeded worm trio remains visible
at `--spread-min 2` (it has `spread = 3`).

### Priority 5 — `ldso` module: skip `exec_target_orphan` check on `include` directives

**Current behavior.** When the `ldso` module emits a record for a
`/etc/ld.so.conf` `include` directive (e.g.,
`include /etc/ld.so.conf.d/*.conf`), the `exec_target` field
holds the include target. The orphan check then runs `os.Stat`
on the target, which fails because the target is a glob, not a
file path. `exec_target_orphan` fires inappropriately.

**Data point.** The fleet-wide signal distribution shows
`exec_target_orphan` on the `ldso` module firing on 43 / 43
non-alpine hosts (43 records). All 43 are baseline `include`
directives shipped by the distro. This is the largest single
source of `exec_target_orphan` records in the fleet (43 of 218
total).

**Proposed change.** In `internal/modules/ldso/ldso.go`, the
helper that computes `execTargetSignals` should short-circuit
when the source line is an `include` directive — globs are not
candidates for the orphan check.

**Expected impact.** 43 baseline `exec_target_orphan` records
collapse to 0. The signal becomes more diagnostically meaningful
when it does fire on ldso (rare): the file referenced really does
not exist.

### Priority 6 — Add Q11 for single-vector mass deployment

**Current behavior.** Q6 catches "polymorphic persistence" — the
same `exec_target_sha256` invoked via different modules across
hosts. Q1 / Q2 are blind to mass-deployment as shown above. There
is no query that catches *mass-deployed implants invoked via a
single module*: a worm that drops 5 cron entries on 5 hosts, each
pointing at byte-identical `/tmp/.cache/.sync/agent`, escapes
both Q6 (no module spread) and Q1 / Q2 (content stacks).

**Data point.** Q6 in this benchmark catches two rows that are
clearly mass-deployed implants but flagged for the wrong reason:

```
5f0602b29a07  4 hosts  /tmp/.s/agent       systemd  spread=1
b651a20a6a04  3 hosts  /tmp/.b/persist     ssh      spread=1
```

These are `systemd-tmp-armed` × 4 instances and `ssh-forced-tmp`
× 3 instances, mass-deployed via a single vector each. They are
mixed in among 42 distro-baseline FPs. If v0.2.0 lands the
`spread_min ≥ 2` filter (Priority 4), these legitimate detections
disappear along with the FPs.

**Proposed change.** Add Q11: "single-vector mass deployment".
Definition (informal): `count(distinct host) >= 3 AND
count(distinct module) == 1 AND exec_target NOT IN
package-baseline-paths`. The "package-baseline-paths" exclusion
list starts with `/usr/bin/*`, `/usr/sbin/*`, `/usr/lib/*`,
`/sbin/*`, `/bin/*`, `/etc/init.d/*`, and is extended in v0.2.0
once provenance via dpkg/rpm is wired in.

**Expected impact.** With Q6 filtered by spread ≥ 2 AND Q11
catching single-vector mass deployments, the combined recall over
the worm-shared trio AND the mass-deployed implants reaches 100 %
with near-zero FPs. Q1 / Q2's limitation (Finding 1 above)
becomes immaterial because Q11 covers the mass-deployment
gap.

### Priority 7 — Q8 per-module threshold or distinct-loci semantics

**Current behavior.** Q8 emits a row per `(host, module)` pair
where the count of records carrying `recent_mtime_7d` is ≥ 5.
The threshold is global; it does not vary by module.

**Data point.** In this benchmark Q8 emits 42 rows — every row
is a `(host, passwd)` pair with 84–96 records and 4 distinct
loci. **Every row is a false positive.** The passwd module's
per-line emission means a single mtime-touched host with the
standard 4 passwd files (`passwd`, `shadow`, `group`, `gshadow`)
produces dozens of records the moment `useradd` runs once — which
the role overlays do for service accounts (gitlab-runner, jenkins,
postgres, redis, alice, bob).

**Proposed change.** Two viable refactors:

A. Per-module threshold: `passwd` requires ≥ 20 records, others
   keep ≥ 5. Tunable per-module in the query.

B. Change semantics to "≥ 3 distinct loci with `recent_mtime_7d`
   in the same module" instead of "≥ 5 records". Distinct loci
   is a more semantic measure than record count because it
   doesn't double-count per-line emissions.

Either change is acceptable. Option B is cleaner conceptually
and shouldn't break other queries.

**Expected impact.** Q8 false positives drop from 42 to ≤ 3.
Real Q8 hits (a malicious sweep touching multiple cron entries
or multiple sshd_config.d drop-ins) remain visible.

### Priority 8 — Q10 highlight outlier module/site_class counts

**Current behavior.** Q10 emits per-host coverage: total records,
distinct modules, distinct site_classes, recent records. It
sorts but does not highlight outliers.

**Data point.** In this benchmark two hosts stand out:
`r-build-server-amzn-01` (13 modules / 19 site_classes vs median
11 / 17 for amzn) and `r-build-server-rhel-01` (13 modules /
18 site_classes vs median 11 / 17 for rhel). Both are compromised
hosts: the `ssh-forced-tmp` implant they carry activates the
`ssh` module (normally silent on hosts without
`/root/.ssh/authorized_keys`), pushing them above their peer
median by 2 modules.

**This is detection by side-channel:** the implant activated a
module that doesn't normally fire on that role / distro combo,
and that mismatch is visible at the Q10 layer without looking at
content.

**Proposed change.** Compute peer-group median for `(role, distro)`
combinations and highlight hosts where `host_modules > peer_median
+ 1`. Same for site_classes. Surface in the HTML report as a
visual badge; surface in the text report as a `*` marker. Not a
hard "this is an implant" claim — just "this host's coverage shape
is unusual for its role; look closer."

**Expected impact.** Adds a second-order detection signal that
doesn't depend on content analysis. Trivial implementation: a
median calculation in `stats.go`. False-positive rate is low
because most legitimate role variation is within ±1 module of
the peer median.

## Reproducing this benchmark

The lab infrastructure is local-only and not part of the public
project. Reproducing the exact numbers in this document requires
the operator to have:

- Docker Desktop or docker-ce, 15+ GB free disk.
- ~1–2 hours of wall time for build + collect + analyze on a
  decent laptop.
- PyYAML available to system Python 3 (`apt install python3-yaml`
  or `pip install pyyaml --break-system-packages`).

The procedure, assuming the operator has the `lab-realistic/`
tree in place:

```sh
cd lab-realistic
python3 scripts/generate_100.py                 # 75-host hostlist
./build.sh --validate                            # ~5 min, fail-fast
./build.sh                                       # full build, ~30 min
./collect.sh                                     # ~5 min for 75 containers
./analyzer/run.sh                                # ~5 s
```

Output: `out/confusion-matrix.md` reproduces the per-query table in
this document modulo minor variance in package-mirror state on the
operator's build day.

Per-iteration package versions drift; this report's specific
numbers are tied to the package state on 2026-05-18 from upstream
apt / dnf / apk mirrors. The qualitative findings (Q4 ∪ Q9
perfect, Q1 / Q2 blind to mass deployment, Q7 precision crashes)
are robust to mirror drift.

## v0.1.0-alpha shippability decision

This benchmark surfaces real weaknesses but does not block v0.1.0-
alpha. The v0.1.0 cookbook's narrative — "the agent collects, the
backend decides" — is internally consistent. What this benchmark
contributes is:

- A measured operational recommendation: **lead with Q4 ∪ Q9**.
- A measured limit: **Q1 / Q2 are not first-pass detectors against
  mass-deployed implants**.
- A measured cost: **Q7 needs three specific refinements before
  it's usable on a 100+-host fleet**.

v0.1.0-alpha tagged on 2026-05-17 is unchanged. v0.2.0 will land
the four refinements in *v0.2.0 priorities* and re-run this
benchmark to demonstrate the improvement. This document then
becomes the historical baseline against which v0.2.0 is measured.
